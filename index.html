Decorators — Why They Exist

A decorator is a function that takes another function, wraps extra behaviour around it, and gives back a replacement. It solves one specific problem: adding the same "before/after" logic (logging, timing, permission checks, retries) to many functions without copy-pasting that logic into every one of them.

Dry Run 1 — one decorator, step by step

NovaMart wants every price-formatting function to print a border before and after it runs. Watch the call stack grow when wrapper is entered, and shrink when it returns.

What the trace proves: @border does not change format_price's own code at all. It replaces the NAME format_price with wrapper. So the line format_price(500) actually calls wrapper(500), which runs the border-print, then calls the ORIGINAL function (kept alive inside wrapper as func), then prints the closing border. The original function never disappears — it's just hidden one layer inside wrapper.

Dry Run 2 — chaining two decorators, step by step

This is the exact ordering question students get wrong in interviews. Watch the call stack carefully — two frames get pushed before the real function ever runs.

The rule the trace demonstrates: decorators WRAP bottom-up (closest to the function wraps first) but EXECUTE top-down (outermost decorator's code runs first when you call it). @bold above @italic above def render_price means: italic wraps render_price first, then bold wraps that already-wrapped version. But when you CALL render_price(500), you are really calling bold's wrapper first — so "bold: before" prints before "italic: before", and "bold: after" prints last, after "italic: after". It unwinds in the exact reverse order it wound up in — same idea as a call stack in any nested function call.

Dry Run 3 — a decorator factory (parameterised decorator)

@retry(times=3) looks like one decorator, but it's actually a function that BUILDS a decorator. Watch closely — there are three nested functions here, each created only when the previous one finishes running.

Why three layers of nesting: a plain decorator only takes func as input. To accept a SETTING like times=3, you need an outer function (retry) whose only job is to receive that setting and then hand back the actual decorator. This outer call — retry(3) — happens once, immediately, the moment Python reads the @retry(times=3) line, which is BEFORE fetch_price is ever called. The decorator it returns is what actually wraps fetch_price.

Seedha vs Ulta — decorator vs copy-pasted retry logic

Seedha (preferred): write the retry loop once inside a decorator, apply @retry(times=3) to any function that needs it.

Ulta (the other way): paste a for attempt in range(3): try/except block inside every single function that needs retrying.

Why seedha wins at scale: if the retry logic needs a fix (say, a delay between attempts), the ulta version means finding and fixing it in every copy. The seedha version means fixing one decorator, and every function using it is fixed instantly.

Modules & Imports — Why Packages Exist

A module is one .py file. A package is a FOLDER of modules that Python can import as one unit. Packages exist so a large project can be split into organised files instead of one 3,000-line script — and so that splitting doesn't break how other code imports it.

Dry Run 4 — building and importing a package

NovaMart's pricing logic lives in a package called shopkit with two files: shopkit/__init__.py and shopkit/pricing.py, used from main.py. Watch which FILE the pointer jumps to at each step — this is the part students usually can't picture.

What the trace proves: import shopkit in main.py does not just "load a file." It runs shopkit/__init__.py from top to bottom. The moment __init__.py hits from .pricing import apply_discount, execution JUMPS into pricing.py and runs THAT file top to bottom too, before coming back. Only after both files have finished running does control return to main.py, at the line right after import shopkit. The dotted .pricing is a relative import — it means "the pricing module inside my own package," which only resolves correctly because __init__.py is being run AS PART OF the shopkit package, not as a standalone script.

Dry Run 5 — the if __name__ == "__main__" guard

Same pricing.py file, run two different ways. Watch how __name__ holds a different value each time, and how that changes what actually executes.

What the trace proves: Python sets a hidden variable called __name__ inside every file it runs. When a file is executed DIRECTLY (python pricing.py), Python sets __name__ to the literal string "__main__". When the SAME file is IMPORTED by another file, Python sets __name__ to the module's own name ("pricing") instead. The if guard is just checking which of those two happened, so test/demo code at the bottom of a file only runs when the file is the one being executed directly — not every time it gets imported somewhere else.

Seedha vs Ulta — specific imports vs star imports

Seedha (preferred): from shopkit.pricing import apply_discount — brings in exactly the one name you need, and anyone reading the file can see exactly where apply_discount came from.

Ulta (the other way): from shopkit.pricing import * — dumps every public name from that file into your current file at once.

Why ulta is risky: if your own file already has a variable or function with the same name as something inside pricing.py, the star import silently OVERWRITES it with no warning. On a small file you might never notice until something breaks in a confusing way.

Standard Library Modules

These are modules that ship with Python itself — no installation needed, just import. Five dry runs below cover the five named in your syllabus: os, sys, math, datetime, pathlib.

Dry Run 6 — os, reading the environment

Enterprise use: a database password or API key should never be typed directly into source code — anyone with read access to the file (or to version control) would see the secret. Storing it as an environment variable and reading it with os.environ.get(...) keeps the actual secret value out of the code entirely. The second argument to .get() is the fallback used if that variable was never set — here, that fallback lets the program keep running (in a limited way) instead of crashing.

Dry Run 7 — sys, reading command-line arguments

What the trace proves: when you run python report.py march warehouse3 from a terminal, Python automatically fills a list called sys.argv with every word typed after python. sys.argv[0] is always the script's own name; sys.argv[1] onward are the extra values the person typed. This is how a script can behave differently depending on what's typed when it's launched, without asking input() questions.

Dry Run 8 — math, rounding the right way

Why three different functions for "rounding": they round in three genuinely different directions. math.ceil() always rounds UP, used when you can't under-deliver (packaging — 4.2 boxes means you need 5 real boxes). math.floor() always rounds DOWN, used when you can't over-promise (4.8 days of stock means only 4 full days are guaranteed). round() rounds to the NEAREST value, used for money and averages where over- and under-estimating are equally fine.

Dry Run 9 — datetime, formatting a timestamp

What the trace proves: datetime(2026, 3, 15, 14, 30) builds one object holding year, month, day, hour and minute together — not five separate variables. .strftime(...) doesn't change that object; it reads it and builds a brand new STRING in whatever layout the format codes describe. %d, %m, %Y are placeholders for day, month and 4-digit year — change their order in the format string and the output's order changes with it, the object itself is untouched.

Dry Run 10 — pathlib, building a file path

What the trace proves: Path("sales") / "2026" / "march.csv" uses the / symbol to join path PIECES, not to divide numbers — Python lets Path objects redefine what / means for them. The result is one Path object that knows its own .suffix (.csv), .stem (march) and .parent (sales/2026) without you ever slicing the string yourself.

Seedha vs Ulta — pathlib vs manual string joining

Seedha (preferred): Path("sales") / "2026" / "march.csv" — lets Python handle the separator correctly no matter what operating system the code runs on.

Ulta (the other way): "sales" + "/" + "2026" + "/" + "march.csv" — hardcodes a forward slash as the separator.

Why ulta breaks: Windows paths use backslashes, not forward slashes. Code built with hardcoded "/" joins can quietly fail the moment it runs on a different operating system than the one it was written on. pathlib was built specifically to make that difference invisible to you.
